# EngineeringOS Beta MVP Strategy

## MVP Thesis

The EngineeringOS beta is successful when one real working engineer can use it every day to move measurably closer to a high-paying product/GCC/FAANG-level role.

The beta should favor a complete guided path over a broad incomplete syllabus.

## First Beta Path

Recommended beta path:

```txt
Current: Senior/Lead Backend Engineer
Target: AWS Solution Architect / Staff-ready Backend Engineer
Outcome: 70-80+ LPA product/GCC readiness and FAANG-level interview readiness
```

This path should cover:

- Backend engineering depth.
- DSA and problem-solving readiness.
- HLD and distributed systems.
- LLD and machine-coding readiness.
- AWS architecture and tradeoffs.
- Staff/architect communication.
- Interview practice.
- Resume, LinkedIn, portfolio, and proof-of-work artifacts.

## MVP Scope

In scope:

- Founder onboarding with current state, target role, weak areas, time budget, and deadline.
- Capability graph for the first beta path.
- Master Syllabus content for the beta path.
- Role roadmap projection from the Master Syllabus.
- Today's Mission as the start screen.
- Topic pages with learning, practice, implementation, interview prep, and proof tasks.
- Readiness scoring split into learning, interview, and offer readiness.
- Progress history and accountability signals.
- Content quality review for high-ROI topics.

## Out of Scope

- Public course marketplace.
- Many simultaneous role paths.
- Community features.
- Billing and subscriptions.
- Public onboarding funnels.
- Automated LeetCode import/sync.
- Real AI generation as a dependency for core content.
- Heavy UI polish that delays the core loop.

## Acceptance Criteria

The beta is ready when:

- One target path is complete enough to follow daily.
- Every high-ROI topic has clear competency proof.
- Today's Mission can choose the next best action from real progress.
- Topic readiness uses Knowledge, Practice, Interview, and Implementation scores.
- Interview readiness is visible separately from learning progress.
- Offer readiness artifacts are tracked separately from topic completion.
- The founder can run a 2-4 week manual beta and identify measurable readiness improvements.

## Build Sequence

1. Freeze the revised product strategy in docs.
2. Define the canonical Master Syllabus schema.
3. Define the Capability Graph schema.
4. Define the first beta target-role projection.
5. Audit current content against the beta path.
6. Fill the highest-ROI beta path gaps.
7. Implement Today's Mission selection from roadmap and readiness state.
8. Implement four-part topic readiness.
9. Separate interview readiness and offer readiness.
10. Run founder manual testing and adjust the path.
